# ORION v2 runtime receipt — owner review only

This document supplements `HOST_APPLICATION_V2_PROCEDURE_REVIEW.md` (SHA-256 `32089d367b133226d6b971d173fda2383a7e595cff4a4e0a62f1ac0224c79399`) under `REVIEW_MANIFEST_20260926_5.json` (SHA-256 `980d467faf416ff1e8848e42c1b9be356ead664eda2b34dfc610b5c7addbe027`). It defines a **proposed** receipt, not an observation or authorization. No host application, DNS/TLS qualification, packet work, or service start has occurred under this proposal. `collision_clearance=false` remains in the review profile.

## Destination and custody

- Proposed future destination: `/var/lib/orion-pilot/host-profile-v2/receipts/application-<UTC-basic>-<128-bit-random>.json`. Do not use a fixed session-named filename or overwrite any receipt. The candidate session directory is not a receipt destination and remains absent before packet preparation.
- The existing `/var/lib/orion-pilot` parent must pass its separate root:`orion-pilot` `0750` custody check. A later authorized application may create only the new `host-profile-v2` and `receipts` directories, each root:root `0700`, with no symlink components. The final JSON is root:root `0600`, regular, one link, and is never made writable by the service account. These proposed directories/files are v2-owned; preserve every older marker, resolver path, unit, session, and receipt.
- Open the directory chain by directory file descriptors with `O_DIRECTORY|O_NOFOLLOW`, verify device/inode/owner/mode, and keep the receipt dirfd for publication. Create an unpredictable temporary file there with `O_CREAT|O_EXCL|O_NOFOLLOW`, mode `0600`; write canonical UTF-8 JSON (sorted keys, compact separators, one trailing newline), flush and `fsync` the file. Reparse it and validate the schema and sanitized-field allowlist. Publish with `renameat2(RENAME_NOREPLACE)` within the same directory, then `fsync` that directory. Never use replacement rename. Compute/report the final SHA-256 externally; do not put the receipt's own digest inside itself. Verify final type, custody, link count, and bytes. A failure after publication leaves an immutable failure/partial receipt for owner inspection, rather than deleting history.
- A staged host cannot be treated as qualified if receipt publication or verification fails. If application rolls back, publish a separate append-only rollback outcome receipt; do not edit the first receipt. A crash before publication is an incomplete transaction requiring root inspection of the temporary file and v2 resources. Cleanup may remove only a verified orphan temporary receipt file, never a published receipt or historical artifact.

Hashes of sensitive policy objects serve as bindings; they do not authorize disclosure. The runtime receipt is not a witness/enrollment receipt, metadata audit database, or authenticated request-attempt count.

## Route comparison and evidence boundary

1. Verify the profile and its disposable route-probe binding before creating a namespace. The probe is fixture evidence only: IPv4 main `2`, IPv4 all-table `7`, IPv6 main `1`, IPv6 all-table `3`; both recorded `fe80::/64` objects have `scope=global`. No probe route is a production observation.
2. In the **new production namespace**, after the approved veth/address/default route are in place, collect fresh `ip -j -details -4 route show table main`, `ip -j -details -4 route show table all`, and the corresponding `-6` commands. Parse JSON arrays, reject parse errors or duplicate/unknown keys, and compare each route as a complete JSON object in a multiset against the corresponding pinned profile array. Do not drop `ifindex`, `metric`, `source`, `scope`, `protocol`, or any other field. Missing fields remain missing. Unexpected dynamic fields fail closed and require a new owner-reviewed profile; no equality exception is silently introduced. Record the production arrays and their hashes separately from the probe hash.
3. On the **host**, collect full IPv4/IPv6 main and all-table route JSON immediately before and after authorized staging, in memory only. Require all baseline route objects to remain equal as complete JSON-object multisets; require no removed entries, no new default or unrelated route, and only the new connected `10.254.205.0/30` route on `orionp0` (with any necessary kernel-generated local-table entries) as additions. Enumerate every added entry and its observed fields in memory; store only approved-/30-sanitized fields and counts/hashes in the receipt. The profile does not pin these host-side route objects, so an exact host route policy PASS is **pending owner review of the production observation**. Do not compare host routes to the disposable namespace probe or invent protocol/metric/source fields.
4. Any namespace route mismatch, unexpected host delta, unavailable snapshot, or leaking customer/global route object fails the staging check. A receipt can report the failure and rollback outcome, but cannot transform a failed observation into clearance. Production namespace equality, host-route delta review, and later DNS/TLS qualification are separate gates.

## Procedure review findings and remaining gates

The existing procedure correctly keeps the namespace inode and nft handles as runtime values, requires fresh collision/stopped-unit checks, preserves historical artifacts, and limits rollback to verified v2-owned identities. This document resolves the previously open receipt destination/schema proposal for **owner review**. It does not modify the procedure or clear its gates. Before any implementation, the owner must approve this destination/schema and the host-route observation policy; a separately authorized application must also have a transaction/crash-recovery design and a newly bound review manifest if the procedure text changes. Host application, DNS/TLS, unsigned subjects, signing, enrollment, and service activation remain unauthorized.
