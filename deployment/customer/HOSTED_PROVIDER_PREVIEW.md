# Auth0 and Google Secret Manager synthetic Preview preparation

This is an **offline configuration contract** for PR #286's hosted portal successor. It does not provision a provider, run a public service, grant ERP access or qualify a customer pilot. `execution_allowed=false` throughout.

## Architecture and current limits

- `review_auth0_metadata` validates operator-fetched Auth0 discovery and JWKS as data. It pins one exact HTTPS issuer, same-origin `/authorize`, `/oauth/token`, `/.well-known/jwks.json`, and reviewed RS256 RSA keys. The host must fetch these documents over direct TLS with size limits, review issuer/domain ownership, then pass them to this function. Unknown or rotated keys deny login until a reviewed reload; there is no automatic JWKS refresh.
- `GoogleSecretManagerVault` is a real REST adapter that uses an injected short-lived OAuth access-token callback. It disables ambient proxies and redirects and pins `https://secretmanager.googleapis.com`. It creates one secret version per synthetic connector reference, validates CRC32C on read, checks tenant/connector scope after retrieval, and deletes the secret on revocation. It never constructs a client credential from browser input.
- `create_auth0_google_portal` composes these reviewed adapters with existing `create_hosted_customer_portal`. It does not open a listener or issue grants. The operator must still supply a persistent `TenantRegistry`, custody-verifying report lookup, reviewed connector/schema and exact synthetic ERP origin.
- The existing Vercel `build_static.py` copies only Command Center assets. The customer WSGI portal and SQLite registry require a separate persistent HTTPS backend. Vercel Authentication on a static Preview does not protect a directly reachable backend origin.
- The current `/customer/api/logout` revokes the ORION session and clears both cookies. It does not terminate the Auth0 SSO session or implement IdP-initiated back-channel logout. If provider-wide immediate logout is a requirement, it needs a separate reviewed implementation and tests before approval.

## Minimum owner provisioning sequence

1. **Identity:** approve or create one dedicated Auth0 **Regular Web Application** for synthetic test users in an owner-selected tenant/region. Record the actual issuer, client ID and exact discovery/JWKS endpoints. Set RS256 signing, authorization code flow, confidential `client_secret_post`, and an exact callback `https://<approved-portal-preview-host>/callback`. No wildcard, customer ERP or canonical callback. Only register a post-logout URL if an IdP logout integration is separately implemented. Store the client secret only in the approved vault under a `vault:oidc-<opaque>` reference; never include it in Vercel variables or source.
2. **Vault:** first check whether an owner-approved vault already supports the three callback methods in `hosted.py`. If none does, approve an isolated Google Cloud Secret Manager project and a billing limit. Enable API and audit logging. Give the Preview workload a keyless, short-lived identity with only the project/resource-scoped permissions required for synthetic create/add/access/delete. No exported service-account JSON key. Privately create an OIDC client secret under Secret Manager ID `orion-preview-oidc-<opaque>`, recorded as `vault:oidc-<opaque>`. The adapter derives connector secret IDs as `orion-preview-conn-<opaque>`; no mapping database is needed.
3. **Persistent backend:** approve an existing Linux host and durable private volume if available. Pin the seven installed distribution hashes and host image. The host supplies a reviewed token callback, Auth0 metadata, persistent SQLite registry, private report custody lookup and WSGI server. Run one backend instance unless shared-state locking is separately qualified. Public TLS proxy must preserve exact Host and HTTPS scheme, strip client forwarding headers, deny direct backend bypass, enforce request/rate limits and route `/customer/*` plus `/callback`. Synthetic ERP egress only, no customer endpoint.
4. **Frontend Preview:** create a **new** Vercel project in `orionteam` only after authorization. Verify effective Deployment Sources and Preview Vercel Authentication. Deploy the pinned static build without secrets, customer APIs or aliases from the existing `hands-ai` project. A future same-origin proxy of `/customer/*` needs separate engineering and ingress review; this static project alone is not the customer portal.
5. **Activation review:** inspect private environment/config references and exact artifact hashes, test direct-backend denial and protected browser route, then request a separate deployment approval. No provider or service is activated by this document.

Current published free allowances are subject to owner terms and use: Auth0 has a Free tier; Google Secret Manager offers six active versions and 10,000 access operations monthly without usage charges, with paid use beyond those limits. A Google Cloud billing account may be required. We do not create one or assume the project will remain free. A small synthetic test can fit within those limits; a real customer deployment needs a separate cost and data-residency review.

Provider references: [Auth0 Regular Web App](https://auth0.com/docs/quickstart/webapp/express/index), [Auth0 pricing](https://auth0.com/pricing), [Google Secret Manager IAM](https://docs.cloud.google.com/secret-manager/docs/access-control), [Google Secret Manager audit](https://docs.cloud.google.com/secret-manager/docs/audit-logging), [Google Secret Manager pricing](https://cloud.google.com/secret-manager/pricing), [Vercel Authentication](https://vercel.com/docs/deployment-protection/methods-to-protect-deployments/vercel-authentication).

## Template contract

`hosted_preview.env.example` is a **review template**, not a loadable current runtime configuration. The private host bootstrap must map its approved entries into `create_auth0_google_portal`; no code path reads the file automatically. Replace every `__REVIEW_REQUIRED__` only through protected host configuration. The Google access token is obtained by a reviewed keyless workload identity callback at runtime and is never stored in this template or Vercel.

## Exact acceptance tests after owner provisioning

- Identity: actual Auth0 login and local logout, one-use code/state, PKCE S256, nonce, RS256 issuer/audience/expiry/kid checks, exact redirect allowlist, rejected wrong or replayed callback, planned signing-key rotation and fail-closed unknown key. Document that local logout does not claim Auth0-wide logout.
- Tenant/session: two synthetic tenants and three users; administrator/analyst separation; membership checked after ID token verification and again per request; denied tenant switch; expired/revoked session; HttpOnly Secure host-only SameSite=Lax session cookie, separate Strict CSRF cookie; denial clears browser report and input state.
- Vault: synthetic connector enrollment stores values only in Secret Manager, registry contains opaque references, tenant/connector substitution denied, corrupted CRC32C denied, rotation/revocation blocks reads, partial failure cleanup, no values in assets/URL/process arguments/logs/responses. Verify audit events and IAM denial.
- Portal: exact persistent report through authenticated API and browser; report source tenant/run/digest matches custody; signed grant proposal remains review-only; grant revocation denies report; restart preserves state and denial history; zero ERP writes and `execution_allowed=false`.
- Ingress: independent TLS/Host check, Vercel Preview SSO check, direct backend bypass denial, no canonical alias or ngrok change, frontend and backend artifact hash match, rollback disables only isolated Preview routes and identities.
- Independent security reviewer signs exact source, installed artifacts, real IdP/vault/ingress, browser evidence and limits before any customer-pilot readiness claim. Stable Ubuntu full suite remains a separate gate.
